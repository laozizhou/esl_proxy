# 早发调度 — Case A

把"已 ready 但尚未下发"的前驱和它的 almost-ready 后继在同一轮共同下发到同一个空闲核,使前驱退休
时后继已经排在队里。

建立在 [Case B](early-dispatch-case-b.md) 之上,请先读那一篇。提示通道、去重、职责划分、链式支持
和验证 harness 都是共用的,此处不再重复。

## 1. Case A 补什么

Case B 要求 P **已经在执行**,这意味着 P 必须曾被排在别的任务后面。而当 P 直接落到一个**完全空闲**
的核上时,Case B 的前提永不出现:P 放置的那一刻核有两个空槽,等到 P 开始执行时,提示的消费点已经
过去了。

Case A 正好覆盖这部分:

```
核 c: slot0 = 空, slot1 = 空          (完全空闲)
  1. send_task 从 ready_queue 取出 P
  2. 把 P 写进 slot0        (先写, 低编号槽)
  3. 把 S 写进 slot1        (后写, 高编号槽)
  4. AICore 从空闲态先看 slot0 → 执行 P → 交替 → 执行 S
```

`P` 必须是**真 ready**(入度 0、已在 `ready_queue` 中),而不只是"尚未下发"。反例:链 `X → A → B`
中 X 未完成时,A 和 B 都恰好有一个未完成前驱、且 A 尚未下发,但 A 此刻不能跑。这就是为什么提示要在
`send_task` 里、**P 被从 `ready_queue` 取出的那一刻**消费——ready 性由构造保证,不需要再推导一次。

## 2. 为什么 Case A 反而是两者中更安全的

"Case B 更安全因为它不依赖仲裁假设"这个直觉在代码层面站不住:

- **Case B** 依据 `free_bitmap` 判断"P 还在飞",而它只在 `read_msgq()` 里刷新。真机上 P 可以在那次
  `READ_REG` 之后任意时刻退休,于是预排可能落进一个**已经空闲**的核的兄弟槽——那正是 Case A 的仲裁
  场景,却是从 Case B 的代码路径走进去的,窗口从纳秒级放大到**小半个 dispatch 轮次**。
- **Case A** 没有这个窗口。P 不可能在被放置之前退休,因为同一次 `send_task` 调用放置两者。两次写
  相邻,且核可证明是空闲的。

所以 Case A 的依赖是**更窄且静态**的(一条仲裁性质,一次性可测),而不是**动态**的(一个随真实 MMIO
延迟而变宽的竞态窗口)。

## 3. Case A 唯一需要的硬件性质

> **核一变空,槽选择就必须回到 slot0——而不是一个仲裁周期之后。**

这条比"从空闲态起 slot0 优先"更尖锐,是实现时被顺序断言抓出来的,不是事前推演出来的。

| 仲裁器 | Case A |
|---|---|
| 永远低编号优先(无相位指针) | ✓ 无条件正确 |
| 相位指针**在核变空的那一刻**复位为 0 | ✓ 正确 |
| 相位指针**下一周期观察到空闲才**复位 | ✗ **先跑 S,顺序反转** |
| 严格交替、从不空闲复位 | ✗ 指针可能停在 1,先跑 S |

第三行是真正的坑,它看起来和第二行只差一个周期,但足以出错:

```
轮 R: 核上 slot0=X 执行中(剩最后 1 tick), slot1 空
 ① X 退休 → 相位指针移到 1(兄弟槽)
 ② dispatch 看到该槽空出 → 核此刻"完全空闲"
 ③ Case A 触发 → P→slot0, S→slot1   (同一轮内)
轮 R+1: 相位指针仍是 1 → 取 slot1 → S 先于 P 执行 ❌
```

关键在于 **dispatch 可以在"最后一个任务退休"的同一轮里就把两个槽都填满**,中间不给硬件留任何"观察到空闲"的周期。所以硬件必须在退休导致核变空时**立即**把选择权交回 slot0。

这也意味着**软件侧无法自保**:dispatch 看不到硬件的相位指针,无法判断"这个核是刚空的还是空了一会儿"。所以这条只能靠硬件保证 + 上真机前实测。

模拟器已按"立即复位"实现([dispatch.c](../esl_proxy/src/scheduler/dispatch.c) 的 `sim_tick`),并保留了顺序断言;把那处复位去掉,断言会在 20 次运行里稳定触发,可以当作断言本身的元测试。

**把 P 放低编号槽**正是同时覆盖两种仲裁器的关键,所以这是硬要求而非约定。第三种是要排除的那个,
而现有代码让它相当可能:因为 `send_task` 至今只用过 slot0,一个不复位的相位指针会永久停在 1,
于是**第一次共发就会先跑 S**。

上真机前必测,两个场景都要:

1. **冷空闲核**:核长时间空闲,写 P→slot0、S→slot1,P 写哨兵、S 校验。0 失败说明空闲态 slot0 胜出。
   再把两个槽对调重跑——失败率接近 100% 才能确认是**槽编号**决定顺序,而不是写入顺序。
2. **刚变空的核**(上面那个坑):先让核跑一个任务 X 占住 slot0,轮询到 X 完成后**立即**共发
   P→slot0、S→slot1。这一场景失败而场景 1 通过,就说明相位指针是"延迟复位"的,**Case A 必须禁用**
   (Case B 不受影响,它不依赖这条)。

## 4. 相对 Case B 的改动

很小 —— Case A 是既有位置上的一条策略,不是新机制。

| 文件 | 改动 |
|---|---|
| `src/scheduler/dispatch.c` | `send_task` 放置 P 之后:若该核**完全空闲**且 `g_hint[P]` 有值,在同一次迭代里把 S 放进兄弟槽 |
| | 独立的 `plants_a` 计数器,使两个 case 在验收输出中可区分 |
| `Makefile_scheduler` | `-DEARLY_DISPATCH_CASE_A`,与 Case B 的开关独立 |

`plant_pass()`、`g_hint[]`、`g_dispatched[]`、同类型判定、延迟模型、顺序断言全部原样复用。

两次写的顺序不能被编译器重排:`REAL_CHIP` 下它们是经 `ctrl_t.aicore_spr_1/2` 的 MMIO store,而那
两个字段声明为普通 `uint64_t*` 无 `volatile`(`include/scheduler/dispatch.h:31-32`)。启用
`REAL_CHIP` 前必须加 `volatile`。

## 5. 新增不变式

Case B 的不变式 1–7 全部继续适用。Case A 追加:

8. **P 取自 `ready_queue`**,故入度为 0 由构造保证。**绝不能**从"尚未下发"推断 ready。
9. **共发时核完全空闲** —— `free_bitmap[type][0]` 和 `[1]` 该位均置。只有一个槽忙的核属于 Case B
   的地盘,不是 Case A 的。
10. **P 占低编号槽,S 占高编号槽**,且按此顺序写入。

## 6. 与 Case B 的关系

按核状态选择,每次放置互斥:

```
完全空闲的核      → Case A (共发 P 与 S)
恰好一个槽忙      → Case B (把 S 排到驻留的 P 后面)
两槽皆忙          → 都不适用
```

`g_hint[P]` 被先触发的一方消费并清除,所以同一个 P 不可能产生两次预排;即便产生,
`g_dispatched[S]` 也会让重复无害。

启用 Case A **不会**减少 Case B 的机会:Case A 只占用 Case B 本来也用不上的核。

**链式场景下两者天然接力**:链首 `D` 落到空闲核时由 Case A 把 `C` 一起发下去;之后 `C` 执行、
`B` 预排、`A` 预排都由 Case B 逐环推进(见 Case B §3)。所以完整的链式流水需要两个 case 都在。

## 7. 预期产出

qwen3 DAG 上合计天花板不变,仍是 **6 / 864 = 0.69%**,见 Case B §10。A 与 B 的分配比例取决于 P 有
多经常被排在别的任务后面,也就是机器的过载程度;32 个可达核、工作量与临界路径比 2.19 倍,两者都
应当出现。

因为天花板由 DAG 结构决定(整张图里只有 6 个任务曾是某个后继"最后一个未完成的同类型前驱"),而不
由机制决定,加上 Case A 不会提高它。它的价值在于覆盖 Case B 结构上到不了的那条放置路径——这对
**正确性覆盖**的意义远大于对吞吐的意义。

**实测**(`EARLY_DISPATCH_CASE_A=1 SIM_LATENCY=1 SIM_TICKS=4`,20/20 次全部通过):

```
plants_case_a + plants_case_b = 6      ← 与天花板一致, 但两者的分配随运行波动
                                          观察到 6A+0B 与 5A+1B 两种
ordering_pairs     = 6 checked, 0 failed
skipped_duplicate  = 6
dispatched_tasks   = 864, completed_task_cnt = 864
```

对比只开 Case B 时的 `plants_b = 6`:**合计不变,只是放置时机换了**。Case A 一旦启用就抢走大部分
机会,因为本 workload 下那 6 个 hub 大多直接落到完全空闲的核上。所以两个 case 覆盖的是**同一批机会
的不同放置路径,不是两个不同的机会集**——这也解释了为什么合计恒等于 6。

另一个实测结论:**Case A 在假完成构建下就可达**(`EARLY_DISPATCH_CASE_A=1` 不带 `SIM_LATENCY`,
同样 6 次预排、8/8 通过)。因为 P 和 S 在同一次 `send_task` 调用里放置,不需要等 P 驻留。所以延迟
模型只是 **Case B** 的前置条件,不是 Case A 的。
