# 阶段二：不变量清单

这是本次移植真正要守住的东西。目标仓的槽位模型、下发路径、数据结构可以跟原型仓完全不同，
但下面每一条都必须成立——**成立与否决定功能对不对，不决定代码长什么样**。

写阶段三指令之前，请对照勘察报告逐条确认：这一条在目标仓靠什么机制成立？如果靠不住，是要
改代码补上，还是这一条在目标仓不适用（要有理由）。

**标记说明**：
- ★ = 违反会产生**静默错误**（能跑、不报错、结果错）
- ⚠ = **原型仓从未验证过**，只在模拟器里成立，上真机前必须实测
- 🔒 = 已知并接受的缺陷，**不要试图"修好"它**，先看清楚为什么不能修

---

## A. hint 的产生（依赖解算侧）

### 1. hint 按【前驱】索引，不是按后继

`hint[P] == S` 表示「S 只剩 P 一个前驱没完成」。

**为什么**：下发侧是在扫描到 P 的时候做决定的，那一刻它手上已经有了 P 的位置信息。按 P 索引
可以直接查表；按 S 索引则需要额外维护一张「task id → 位置」的反查表。

**原型实现**：`g_early_hint[RING_SIZE]` / `g_cross_hint[RING_SIZE]`，下标是 P 的 task id。

### 2. 发布时机是「S 的未完成前驱数降到 1」，且必须有两个发布点

**为什么**：只挂在「入度递减」那一处会漏掉纯链式任务——一个只有一个前驱的任务，它的入度从
初始化起就是 1，永远不会发生「跳变到 1」这个事件。

**注意计数的口径**：这里说的是**运行时未完成前驱数**，不是图里的静态前驱个数。原型在提交
任务时算的就是「有几个前驱还没完成」，不是 `pre_cnt`。挂错口径不会报错，只会静默损失掉纯
链式那部分覆盖率。

**移植确认**：勘察 E4（递减点）、E6（提交点）。

### 3. ★ 同类型/跨类型的分类是静态的，且类型表必须**完整**

分类本身启动时算一次即可。但有一个前提容易漏：**参与分类的每一个 task id 都必须在类型表里
有真实的值**。

**为什么**：原型里 `g_early_type[]` 只对图中出现过的 id 赋值，其余保持零初始化——而 0 恰好
是一个合法类型值（cube）。任何类型没被登记过的前驱都会被静默当成 cube。

**违反的后果**：一条跨类型的边被误分类成同类型 → S 被种到 P 的兄弟槽 → **完全没有通知机制**
却依赖跨单元的顺序 → 静默的顺序错误。

**移植确认**：目标仓如果任务是增量提交的、或 id 空间是稀疏的，必须确保分类发生时类型表已经
填全，或者给未登记的 id 一个不会被误判的哨兵值。

### 4. ★ 对单个 S：先查同类型，找不到才查跨类型；两者互斥

**为什么**：调用时已经保证「任意类型的未完成前驱总共只有 1 个」。它的任意子集里未完成的最多
也只有 1 个——所以现场遍历找到第一个未完成的就是答案，不需要任何额外计数器。

**违反的后果**：写成「两个列表都查、都发布」的话，同一个 S 会被两条路径各种一次 → 重复下发。

## B. 触发条件的安全性

### 5. ★★ 判断依据只能用 AICPU 可观测的信息

能用的只有「任务已下发」和「任务已完成」这两类信号衍生出来的东西。**绝对不能用任何反映任务
内部执行进度的状态**——比如「这个任务是真的在算，还是卡在某个等待里」。

**为什么**：真机上 AICPU 看不到计算单元内部。原型仓的模拟器里技术上能查到（都在同一个进程
里），但一旦这么写，测出来的结论就搬不到真机上。

**这一条在原型开发过程中被踩过一次，很隐蔽。** 写阶段三指令时，逐个检查每个判断条件的数据
来源。另见不变量 24——那里有一个"看起来该修、但一修就违反本条"的陷阱。

### 6. ★⚠ 只对「确定是所在单元上唯一活跃者」的前驱做早发

不能只判断「P 被下发了」，必须判断「P 前面没有任何东西挡着」。

**为什么**：如果 P 前面还排着别的任务 P0，那 P0 会先完成。跨类型场景下尤其严重——通知是按
单元寻址、不认任务身份的，P0 完成时发出的通知会被 S 误当成「P 完成了」而提前解除阻塞，
**而这时 P 可能还没开始算**。

**原型实现**：「这个核恰好一个槽忙」——有序两槽下，一个核只驻留一个任务时它前面必然没东西。

**⚠ 但这个判据在原型里还隐含了一层真机上不成立的东西**：它同时被当作「P 此刻还在跑」来用，
而这只在模拟器里为真——模拟器的时钟是在同一个函数里同步推进的，占用状态永远是精确的。真机上
占用状态来自一次寄存器读取，**P 完全可以在那次读取之后、放置之前退休**。这个窗口在真机上从
纳秒级放大到接近一个下发轮次。后果见不变量 19。

**移植确认**：勘察 A1/A2/A6/A7、L 组（快照时效性）。**如果目标仓无法用可观测信息表达出等价判断，整个功能都不应该
做**，先停下来讨论。

### 7. ★★⚠ 同类型 S 的落点必须是硬件在 P 之后才会去看的位置

这条是整个功能里**风险最高**的一条，而且**原型仓从未在真机上验证过**。

同类型早发不带任何通知机制，S 能在 P 之后才开始，完全靠硬件执行同一个单元上多个任务的固有
顺序。但「有序」这个词是模糊的，而最自然的一种理解恰恰会让主路径出错。

**原型仓 `doc/early-dispatch-case-a.md` 里的仲裁器真值表**：

| 仲裁器行为 | 后果 |
|---|---|
| 永远低编号槽优先 | P 在低槽时安全；**P 在高槽、S 被种进低槽时，S 先跑** ❌ |
| 相位指针在核变空的**那一刻**复位到低槽 | ✓ 两种情况都安全 |
| 相位指针**下一周期**才复位 | ✗ 先跑 S，顺序反转 |
| 严格交替、从不复位 | ✗ 指针可能停在高槽，先跑 S |

**为什么现在比原设计更严格**：早发的两条路径已经合并成一次统一扫描，而扫描时 S 是被放进
**当时恰好空着的那个槽**——它可能比 P 的槽编号更低。所以现在需要的是上表**第二行**那种仲裁器，
比原设计里任何单独一条要求都强。

**软件侧无法自保**：下发侧看不到硬件的相位指针，无法判断「这个单元是刚空的还是空了一会儿」。

**上真机前必须实测**（原设计文档给了具体做法，照做）：
1. **冷空闲单元**：长时间空闲的单元，同时下发 P→低槽、S→高槽，P 写哨兵、S 校验。0 失败说明
   空闲态低槽优先。再把两个槽对调重跑——失败率接近 100% 才能确认是**槽编号**决定顺序，而不是
   写入顺序。
2. **刚变空的单元**：先让单元跑一个任务 X 占住低槽，轮询到 X 完成后**立即**同时下发 P→低槽、
   S→高槽。场景 1 通过而场景 2 失败，说明相位指针是延迟复位的——**同类型早发必须禁用**。

**在这两个测试通过之前，不要打开同类型早发。**

**移植确认**：勘察 K 组（尤其 K2/K3）、A5/A7。另见不变量 21（编译器重排会在另一个层面制造同样的错误）。

### 8. 跨类型 S 的落点必须是**完全空闲**的目标单元

不允许把 S 排到一个已经有任务的位置后面。

**为什么**：S 本来就要等 P 的通知；如果还要先等前面排队的任务跑完，就是双重等待，收益基本被
吃光，而占着资源的代价照付。

### 9. 跨类型的配对关系必须真实成立

原型假设：cube 第 i 号 ↔ vector 第 i 号，严格一对一。

**移植确认**：勘察 F2/F3。**如果目标仓不是同编号一对一，不要自行修改映射公式**——这会连带
影响通知该发给谁、S 该放到哪一个候选单元，属于重新设计，需要单独讨论。

## C. 唯一性与消费规则

### 10. ★★ 每个任务恰好被下发一次

一个已经被提前下发的任务，等它自己的入度归零时照样会走到正常下发路径，必须在那里被拦下。

**违反的后果**：重复下发 → 完成被上报两次 → 依赖解算把每个后继的入度多减一次 → 后继在真实
前驱还没跑完时就被放行。**整个 DAG 的执行顺序错乱，且不报错。** 这是后果最严重的一条。

这一条有四个独立的子要求，缺一不可：

**10a. 标记必须在每一个放置点置位。** 原型只有一个放置原语，所以只有一处。**目标仓已知把
slot 的下发拆开了，可能存在多个放置点——每一个都必须置位，漏掉的那条就是缺口。** 最稳妥的做法
是先把它们收敛成一个共用出口。

**10b. ★ 拦截必须放在下发点，不能放在依赖解算的就绪门上。** 这是原设计的刻意选择：在就绪门
上抑制 S，等于把它从**唯一还能救回它的路径**上不可撤销地移除——一旦软件预排成功而硬件没执行，
S 永久丢失且无声死循环。放在下发点跳过，就绪队列始终是活的兜底，不需要看门狗。

> 「为什么不在产生的时候就不放进队列」是一个看起来更整洁、很容易被提出来的重构。**它会摧毁
> 唯一的恢复路径。** 推论：放弃一次早发永远是安全的；条件建立不起来时，正确动作就是不种。

**10c. ★ 这个标记必须是单写者，或者是原子的。** 原型的整套无锁设计建立在「所有任务都流经
同一个下发线程」之上（原型里就绪队列的目标下发线程被硬编码成 0，所以第二个下发线程实际收不到
任何任务）。如果目标仓有多个下发上下文可能并发地取到同一个任务、或并发地扫描早发候选，这个
普通字节就会出现「检查—置位」竞态：两个上下文都读到 0、都下发 → 重复下发，正是本条要防的
灾难在它自己底下被重新引入。

**目标仓是真机、有多个计算单元，按 die 或 cluster 分开的下发循环是很可能的形态。** 勘察 I 组问题就是为了确认这一点。

**10d. 任务 id 在整个运行期内必须唯一、不可复用。** 原型的标记数组**从不清零**，靠的正是
「id 不复用」这个前提。如果目标仓的 id 会回绕：每个被复用的 id 一上来就读成「已下发」→ 在正常
下发路径里被永远跳过 → 它的后继永远解不开 → **DAG 静默挂死**；如果 id 还可能超出数组上界，
那就是一次越界写。

**注意原型里的一处不一致**：依赖解算侧用了 `& RING_MASK` 掩码，下发侧直接用裸 id 索引。原型
安全只是因为 id 恒小于数组大小。

### 11. 同类型 hint：不管种没种成功都消费掉

**为什么**：条件成立时（兄弟位置已经空着）必然放得下，唯一的失败原因只可能是「S 已经被别的
路径下发过了」。留着它只会对着一个早已退休的前驱无限重试。

### 12. 跨类型 hint：只在「成功」或「已过期」时消费，目标忙时**保留**

**为什么**：「目标单元这一刻忙」不等于「这条 hint 过期了」，留着还有下一轮的机会。这一条跟
第 11 条不对称，是刻意的，不要图省事统一成一种写法。

**⚠ 但原型的注释在这里给了一个错误的理由**，别照抄那个理由：它说「P 在退休前会一直是自己单元
上唯一的占用者，下一轮还会被扫到」——**这不成立**。同一轮里稍早的同类型分支可能已经把 P 的
兄弟槽填上了，正常下发路径也可能在后续任意一轮把任务排到 P 后面。任何一种都会让 P 不再满足
「唯一活跃」，于是这条被保留的 hint **再也不会被重新扫到，就此滞留**。

结论（保留）仍然是对的——保留至少还有机会，消费掉就一定没有了——但要知道这是**有损的**，不是
「早晚会成功」。

### 13. ★ 对单个 P：同类型和跨类型是两个独立的检查，不是二选一

一个 P 完全可能同时是一个同类型后继和一个跨类型后继各自的最后一个前驱。检查时必须是**并列的
两个判断**，不能写成 `if / else`。

**跟第 4 条不冲突**：第 4 条说的是「对单个 **S**，只会有一个前驱是它的幸存者」；这一条说的是
「对单个 **P**，可以有多个不同的后继在等它」。方向不同。

## D. 时序

### 14. ★ 早发的扫描必须在当轮**所有**正常下发之后

**为什么**：早发盯上的位置，同时也是就绪队列里真实任务可以拿走的位置。扫描放在前面，就会让
早发抢在一个「拿到就能立刻开始跑」的真实任务前面——用一个实打实的损失去换一个投机收益。

**这一条在原型上是实测验证过的**：挪到后面之后早发成功次数明显下降，少掉的正是原本被抢走的
那部分。

**附带好处**：本轮刚被下发到空闲单元的前驱，等扫描跑到时已经是普通的「唯一活跃」候选了——所以
**不需要为「前驱和后继同时下发」单独写一条代码路径**。原型早期有过这样一条，正是因为这个顺序
调整才被证明多余、删掉了。

**移植确认**：目标仓一轮里的下发调用可能不止三次、也可能不按类型划分——要求是「在**全部**正常
下发之后」，不是「在第三次调用之后」。

### 15. ★ 早发的扫描有**两个**前置顺序要求，不是一个

**15a. 必须在完成信号被翻译成 task id 并消费完之后。** 放置任务会覆写「位置 → task id」的
反查表，而完成信号正要靠这张表翻译。先种的话，一个正在退休的任务的完成会被上报成**被种进去
那个任务**的 id——真正完成的任务永远不会被上报（DAG 卡死），被种进去的任务在还没跑之前就被
当成完成了。

**15b. 必须在占用状态吸收完本轮的完成之后。** 否则一个**已经退休**的 P 仍然读起来像是所在
单元的唯一占用者。同类型场景下这只是白种一次；**跨类型场景下这正是不变量 19 的死锁序列**。

**移植确认**：勘察 C2/C3/C4/D1——要同时找到「完成已翻译」和「占用状态已更新」这两个点。

## E. 前提条件

### 16. 一个计算单元必须能同时驻留两个任务，且第二个排在第一个后面

没有排队能力，就无法把后继放到一个还在执行的前驱后面。

**移植确认**：勘察 A6。**目标仓已知把 slot 的下发拆开了，这个前提很可能本来就满足**——如果是，
这一条不需要任何改动。不要机械照搬原型仓的改法。

**配套要求**：如果为此放宽了「哪些单元算候选」的条件，一轮里**能取多少个任务的上界也要跟着
改**——原型里这两者是绑死的，取多了会拿到放不下的任务，然后对空位图做位扫描，结果未定义。

### 17. ★ 不能有「把一种类型的空闲状态与另一种类型按位与」的操作

**为什么**：这类操作只会清空闲位、不会恢复。一个单元被 A 类型任务占用时会连带丢掉自己的
B 类型资格，而 A 类型完成时只恢复 A 类型的位——B 类型那个位再也回不来。

**为什么以前没暴露**：只要任务是「下发当轮就完成」的模型，这个与运算永远是空操作。**而本功能
的前提恰恰是任务开始跨轮驻留**——一旦驻留，B 类型那一半的任务会全部饿死。

**移植确认**：勘察 H2。存在且被调用的话，必须停用这次调用。

### 18. ★★ 打开开关就隐含「计算单元侧的通知机制已经就位」

跨类型早发的顺序保证**完全依赖**计算单元侧的等待/通知实现。原型有一个编译期守卫强制这一点，
但那个守卫在目标仓没有等价物可写（跨仓库，编译期查不到）。

**违反的后果**：跨类型的 S 会在 P 还没完成时直接开始算，**静默的正确性错误**。

**注意**：把同类型和跨类型合并成一个开关（本次移植的决定）意味着**同类型那一半也被这条卡
住了**——尽管它根本不需要通知机制。如果想先让同类型上线跑起来，需要重新考虑是否拆成两个开关。
不过原型实测的收益分布是同类型个位数、跨类型两三百次，同类型单独上线的价值有限。

### 19. ★★⚠ 真机上占用状态是**快照**，跨类型路径对此没有任何防御

这是原型仓**结构上不可能遇到、真机上一定会遇到**的一类问题。

原型的模拟时钟是在同一个函数里同步推进的，所以从读取占用状态到放置任务这段时间里，不可能有
任何任务退休——占用状态永远精确。真机上占用状态来自一次寄存器读取，之后 P 随时可能退休。

**死锁序列**：
1. 读取占用状态，P 显示仍然驻留
2. P 实际退休，并按 kernel.h 的语义**向配对单元发出了通知**
3. 扫描仍然认为 P 是唯一占用者 → 找到 hint → 目标单元空闲 → 把 S 放上去并置等待标记
4. 清空邮箱这个动作**把 P 刚才那次已经送达的通知丢掉了**
5. S 等一个永远不会再来的通知 → **静默的无限停顿，可能是永久死锁**

**跟 `port_0_workflow.md` 里提到的那个竞态是两回事**，但症状相同。那里给了两个解法方向，
**只有第二个（把通知从电平标志改成计数器/边沿语义）能同时覆盖这一条**——而且必须由 AICPU 在
放置时刻取基线，否则一个单纯累加的计数器会让不相关的更早的通知也把 S 解除阻塞，那正是不变量 6
要防的错误。

**移植确认**：勘察 L 组问题。这条必须在设计 kernel.h 通知机制时一并解决，不能事后补。

### 20. ★ 早发路径必须完成正常下发路径的**全部**每任务义务，不只是置个标记

原型靠「只有一个放置原语」在结构上保证了这一点。

目标仓的正常下发路径除了写槽位，很可能还做别的事：敲门铃、登记在飞任务表、递减某个信用计数、
更新反查表、消息队列簿记……**这些在早发路径上一样都不能少**。

**违反的后果**：被种的任务在硬件上跑了，但它的完成没有被归属；或者槽位的占用账目慢慢漂移。
症状是 DAG 挂死，或者槽位泄漏到最后没得可发。

**这是本次移植最可能出问题的地方**——恰恰因为目标仓的下发路径被拆开过，有时间各自积累出不同
的簿记动作。勘察 Q 组问题就是为了把这些挖出来。

### 21. ★⚠ 下发字的写入需要 `volatile` 或等价的顺序保证

原型仓里下发用的指针是普通指针，没有 `volatile`——原设计文档明确写了「启用真机前必须加」。
原型从来没走过真机路径，所以这条从没被触发过。

**为什么对本功能尤其致命**：P 的写入和 S 的写入发生在**两次独立的调用**里，中间没有任何屏障。
编译器可以自由地重排或下沉非 volatile 存储，让硬件先看到 S 的写入——**这会在编译器层面重新
制造出不变量 7 的顺序错误**，而且跟仲裁器行为无关，测硬件也测不出来。

**移植确认**：勘察 M 组问题。

### 22. 每个标记为忙的位置都必须有有效的反查表条目

扫描时会拿反查表的内容直接去查 hint 数组，中间没有任何校验。原型安全是因为：不存在的单元在
两个槽上都被初始化成「忙」（于是被「恰好一个忙」的判据排除掉），而每一个「忙」位都是放置动作
设置的，同时就写了反查表。

**移植确认**：目标仓如果对保留/禁用/故障的单元有不对称的表示，或者在复位时就把某个槽标成忙，
就会产生一个幽灵候选，反查出来的是垃圾值，然后拿它去索引 hint 数组。

### 23. 一次性初始化的时机和哨兵值

**23a. 时机**：必须在任务图已知之后、第一轮下发之前，执行且仅执行一次。原型放在下发侧控制块
初始化之后、创建工作线程之前。

**23b. ★ 哨兵值**：hint 数组必须被显式初始化成「无」这个哨兵（原型用 `0xFFFFFFFF`），
**不能只是清零**——0 是一个合法的 task id。如果只清零、或者初始化函数根本没被调用到，那么每
一个驻留任务读起来都像是「有一条指向任务 0 的待发布 hint」，扫描会把任务 0 反复种出去。

这是一个很容易踩的组合：写了初始化函数、但忘了接上调用点，产生的恰好就是这个静默错误。

## F. 已知并接受的缺陷（不要"修好"它们）

这两条原型仓都讨论过、都决定接受。写在这里是为了让实现者**知道它们存在且是有意的**，不要
自作主张去修——其中一条一修就会违反不变量 5。

### 24. 🔒 「早发的早发」：被阻塞的早发任务，看起来跟正在跑的一模一样

一个跨类型早发的 S 落到目标单元后，那个单元就是「恰好一个占用者」，而扫描只看占用状态——它
**分不出 S 是在算还是卡在等通知**。所以如果 S 恰好又是某个任务 S1 的唯一同类型前驱，S1 会被
照常种到 S 旁边，然后被 S 的整个「等待 + 执行」时间一起拖累。

**为什么不能修**：要过滤这种情况，就得去读「这个任务是不是在等」——**那正是不变量 5 明令禁止
的事**。任何"修好"了这一条的实现，都已经违反了不变量 5。

**还有一个原型文档里没写的连带后果**：一个完全正常的就绪任务也可能被排到被阻塞的 S 后面（下发
路径只要有一个槽空就会选中这个单元）。在有序槽语义下，这个真实任务会被**队头阻塞**在一个自己
都还在等待的投机任务后面。模拟器里等待时间短，看不出来；真机上跨类型的等待可能很长，这是实打
实的吞吐风险。

### 25. 🔒 跨类型的等待没有任何超时、看门狗或死锁检测

同类型早发不需要看门狗，因为就绪队列始终是活的兜底（见 10b）。但一个**已经被放上去、正卡在
等通知**的跨类型 S 没有兜底——它已经不在就绪队列里（标记已置位），就停在硬件上。

模拟器上无限等待只是测试挂住；**真机上是一个卡死的计算单元和一次挂死的推理**。原型明确把
超时机制列为"本轮不做"。实现者需要自己判断真机是否需要一个原型没有的超时。

### 26. 🔒 只覆盖「恰好一个槽忙」，两个槽都忙的单元被整体排除

这不是因为不安全，而是因为两个槽都忙时，占用状态**分不出这两个里哪个在跑、哪个在排队**。

这是最容易被想去放宽的地方（「明明也是安全的，为什么不做」）。放宽之前先想清楚：如果排在前面
的那个先退休并发出通知，等待中的 S 会把它误当成自己等的那个——**那就掉进不变量 6 要防的真
错误里了**。要放宽，需要先有一份「谁先放上去」的记录，那是新机制，不是调一下判据。
