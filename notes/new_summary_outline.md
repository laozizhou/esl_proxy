# 早发调度：方法提纲

分支：`dev/early-dispatch-cpu-free`

面向一页自读材料的提纲，文字须独立成立，图为辅助。
改动过程与踩坑记录见 [counter_and_xor.md](counter_and_xor.md)。

---

## 背景

任务完成到其后继开始执行之间，需经过一次完整的通知与解析流程：引擎置完成标志、
dispatch 读取并推入完成队列、painter 解除依赖并投入就绪队列、dispatch 再次下发。
该流程跨越两个线程，至少占用两个 dispatch 轮次，期间对应引擎处于空闲状态。

## 概述

硬件形态：每个计算核包含 cube 与 vector 两种引擎，每个引擎具备两个任务槽位；引擎
非抢占，两个槽位中同一时刻仅有一个任务处于执行状态。

当后继任务 S 仅剩一个未完成前驱 P 时，不等待 P 退休，提前将 S 下发至 P 所在的计算核。
P 退休后 S 即可开始执行，上述通知与解析流程与 P 的执行并行完成。

本方案将 S 的落点限定在 P 所在核内，这是后续各项机制成立的前提。

## 1. 识别与记录（painter 侧）

为每个任务维护一个异或累加器，初值为其全部未完成前驱的异或和，前驱完成时将其异或
移出。入度降至 1 时，累加器中的剩余值即为唯一未完成前驱 P，无需查表或遍历前驱列表。

随即登记 `hint[P] = S`。该表以前驱 P 为索引而非后继 S，原因见下一节。

## 2. 触发与消费（dispatch 侧）

dispatch 在每轮正常下发之后扫核：对每种引擎类型，取两个槽位空闲位图的异或，结果中
置位的核即"恰好一个槽位在忙"。该核上没有任何任务排在当前占用者之前，因此占用者即为 P。

取得 P 后查询 `hint[P]`，命中则执行早发。访问路径为"先定位槽位、再查询占用者"，
按 P 索引的 hint 表可在此处直接命中，无需维护任务到位置的反向映射。

该条件同时限定了早发的触发频率：实测每轮平均仅 0.08 个核满足，约 92% 的轮次无候选。

## 3. 同类型落点

S 与 P 类型相同时，将 S 放置于 P 的兄弟槽位，即同一引擎的另一槽。

```
核 7 · cube 引擎
┌─────────┬─────────┐
│  槽 0   │  槽 1   │
│    P    │    S    │
└─────────┴─────────┘
```

引擎非抢占且两槽同时仅有一个在执行，P 退休后引擎方才切换至兄弟槽，执行顺序由硬件
仲裁器保证。该路径无需任何通知机制，下发时不附加额外字段。

## 4. 跨类型落点

S 与 P 类型不同时，将 S 放置于同一核的另一种引擎。两个引擎并行执行，仲裁器不提供
跨引擎的顺序保证，因此需要显式信号。

```
核 7
├── cube   引擎 ── P 执行中
└── vector 引擎 ── S 驻留等待
```

下发 S 时携带目标值 `target`，取 P 在其所在引擎上的放置序号。S 驻留于槽位等待，直至
对面引擎的退休计数器达到 `target`。该判断为绝对值比较而非边沿等待，因此即使 S 在 P
退休之后才完成放置，结果依然正确。

| | 同类型 | 跨类型 |
|---|---|---|
| 落点 | P 的兄弟槽位 | 同核另一种引擎 |
| 顺序保证来源 | 硬件仲裁器 | 退休计数器 + 目标值 |
| 下发时附加字段 | 无 | `wait_target` |
| 实测占比 | 约 10% | 约 90% |

## 5. 实验结果

测试用例为 qwen3，共 864 个任务，其中 6 个无前驱。单次运行发布 hint 858 条，即除
无前驱任务外全部覆盖，为理论上限；触发早发约 290 次。

顺序断言覆盖全部早发任务对，检查 S 的开始时刻不早于 P 的退休时刻，在 `SIM_TICKS`
取 1、2、4、8、16 各档下结果均为 0 失败。

当前仿真器无法给出有效的吞吐量度量，本文不就吞吐收益作结论。

## 6. 总结与边界

已实现单核范围内的完整早发链路：painter 侧的幸存前驱识别与 hint 发布；dispatch 侧的
扫核触发；同类型与跨类型两条落点路径；跨类型的计数器等待机制；仿真器侧的执行顺序验证。

早发次数的主要约束有两项：扫核条件（每轮平均 0.08 个候选核），以及 hint 表对每个前驱
仅保留一个表项——实测 858 条 hint 落在 516 个不同前驱上，约 39% 的发布会覆盖尚未被
消费的表项。hint 供给不构成约束。

落点限定于单核范围内。跨核扩展需先解决落点选择策略与槽位占用导致的死锁问题。

待硬件确认的前提：

1. 空闲引擎优先选取槽位 0。同类型落点的顺序保证与跨类型目标值的有效性均依赖此项。
2. 每个引擎维护一个单调递增、不清零的退休计数器。
3. 下发字在 `task_id` 之外可携带一个目标值。

跨类型路径目前由 `#error` 限制，仅能在 `SIM_LATENCY` 下编译。本阶段的意义在于：
跨类型通知机制由"设计不成立"转为"设计成立、硬件侧未实现"。
