    02结论

    一页读完

    两条通道,各有对应物
    我们的机制AMDNVIDIA
    同类型
    S 放进 P 的兄弟槽,靠槽仲裁顺序接续,不需要任何通知    		 AQL packet header 的 barrier bit 同一 stream 的按序语义
    跨类型
    S 放到对面引擎,带「先等信号」标志,P 退休时写信号    		 barrier-AND packet + completion signal cuStreamWaitValue64 / event

    这不是巧合。「让后继提前就位、由硬件而不是软件回路来放行」是同一个问题, 三家都独立走到了同一个分岔口:要么排在按序队列里(不需要信号),要么显式等一个信号。

    我们自己列的缺陷,工业界给的答案更强
    形态比较方式要清零吗
    我们现在 1 bit == 1 要 —— 且真机上挡不住陈旧信号
    我们设想 只增计数器 带次数 不用
    NVIDIA 64 位单调值 cyclic GEQ 永远不用 —— 循环比较忽略回绕
    AMD int64_t signal 完成时原子递减,等 0;或掩码条件 不用

    而有三处我们的设计,没有找到哪家把它做成暴露的原语 —— 匿名的引擎级完成信号加上 free_bitmap 异或不变量、提示按 P 键入、 以及所依赖的那条槽仲裁性质。近似物和学术前例见第 08 页。

    03对标基准

    被对标的是什么

    为了让后面几页有共同的参照,先把我们机制里与对标相关的那几条摘出来。 完整描述见 early_dispatch_summary.html。

    机制骨架
      painter   解依赖
              ├─ 入度归零 ─────────────► ready_queue
              └─ 只差一个前驱 ────────► hint[P] = S
                 两个发布点:resolve_dep 递减到 1,以及 add_successors
                 提交时入度即为 1(纯链式永远不发生「降到 1」的跳变)

  dispatch  一轮之内:
              ① 读完成标志,推进 completed_queue
              ② send_task —— ready_queue 先发,早发只捡剩下的槽
              ③ 扫核:free_bitmap[type][0] ^ free_bitmap[type][1]
                   恰好一个槽在忙 ⟹ 这个引擎上没有任务能先于 P 退休
                   └─ 查 hint[P] ─┬─ 同类型 ─► P 的兄弟槽(槽 ^ 1)
                                  └─ 跨类型 ─► 同核对面引擎(类型 ^ 1)的槽 0
                                                  要求该引擎两槽全空

  去重        g_early_dispatched[task_id] —— dispatch 唯一 send 点,同时覆盖两条路
    两条通道靠什么等到 P
    通道S 放在哪靠什么等到 P提示的处置
    同类型 P 的兄弟槽(同一引擎) 不需要通知 —— 靠仲裁本身 条件成立必然放得下,取到就无条件消费
    跨类型 同核对面引擎的槽 0,要求两槽全空 P 退休时往对面写信号,S 读到才开跑 「目的地忙」不等于过期,保留重试

    两条通道的机会并不对等:全图 2742 条边里, 同类型只有 180 条 —— 约 6.6%。 这个失衡后面第 09 页会回来讨论,它决定了工程投入该压在哪。

    两个已知缺陷:① 通知是一个 bit,真机上站不住(清零来自 CPU 侧、写 1 来自引擎侧, 两者没有顺序保证,而一个 bit 分不出新旧);② 每个 P 每条通道只有一格提示, 机制走不出这个核。这两条是第 07 页的对标重点。
    04AMD · AQL

    两条通道的规范级对应

    AMD 的 HSA / AQL 是规范公开、参考实现开源的,对我们参考价值最高 —— 能读到 packet 的确切位域,而不是只能读 API 语义。

    同类型 ↔ barrier bit
    hsa.h · HSA_PACKET_HEADER_BARRIER 的文档注释
    Barrier bit. If the barrier bit is set, the processing of the
current packet only launches when all preceding packets
(within the same queue) are complete.
    HSA SysArch 1.2 · §2.9.2 —— 规范自己的措辞更能说明问题
    All preceding packets in the queue must have completed their
    launch phase.
...
If the barrier bit in the packet header is set then all preceding
packets in the queue must have completed.

    规范这两句连起来读才有意思:默认只保证前面的包都「启动过」, barrier bit 把它升级成「前面的包都已完成」。

    这正是我们同类型通道的处境 —— 光有槽的先后不够, 还得保证 P 退休之后 S 才被取走,靠的就是那条「核一变空立刻回槽 0」的仲裁性质。 AMD 把这一步做成了包头里的一个位,我们靠时序性质。

    跨类型 ↔ barrier-AND packet
    hsa.h · 结构体原文;位域与 SysArch 1.2 Table 2-9 一致
    typedef struct hsa_barrier_and_packet_s {
  uint16_t     header;
  uint16_t     reserved0;
  uint32_t     reserved1;
  hsa_signal_t dep_signal[5];        // 最多等 5 个依赖信号
  uint64_t     reserved2;
  hsa_signal_t completion_signal;    // 完成时被原子递减
} hsa_barrier_and_packet_t;

    1. dep_signal[5] —— 硬件层面的扇入上限是 5

      超过 5 个前驱就串接多个 barrier packet。这是一个真实的工程折中数字, 对我们有直接参考意义 —— 我们的图入度均值 3.17、最大 16。

    2. handle 为 0 的信号被当作「依赖已满足」

      barrier-OR 里反过来:handle 0 被当作「依赖未满足」。 这让定长 packet 支持可变扇入 —— 不用为扇入 2 和扇入 5 准备两种包格式。

    3. completion_signal:完成阶段被原子递减

      这是一个倒数到 0 的 join counter。初值设成「要等几个」, 每个完成方递减,等待方等 0。

      有一条容易漏掉的约束:规范 §2.9.8 说 barrier-AND 只保证在所有信号 「become zero and remain zero until the barrier-AND packet completes」时才完成 —— 要抄这个形状的话,零值必须保持,不能被下一轮立刻重置。

      对我们另有一个用处:SPMD 任务的 count 个 block 本身就是一次「count 对 1 的汇合」,这个原语的形状正好是它。

    更灵活的一个:barrier value packet
    ROCR-Runtime · hsa_amd_barrier_value_packet_t(AMD 扩展)
    Halts packet processing and waits for
    (signal_value & ::mask) ::cond ::value
to be satisfied, where signal_value is the value of the
signal ::signal.

    带掩码的条件等待,表达力比单纯的「等于 0」强得多。 这是 AMD 自己的扩展(包类型 HSA_AMD_PACKET_TYPE_BARRIER_VALUE), 基础 HSA 规范里只有 barrier-AND 和 barrier-OR,没有它。

    信号与队列
    项规范/文档说法
    hsa_signal_value_t large machine model 下 int64_t,small model 下 int32_t
    doorbell 单调性 队列类型为 single producer 时,doorbell 值必须单调递增, 且通知包 ID 之前的所有包必须已经分配好
    队列形态 packet processor 按环形缓冲处理;size 是最大可容纳包数,必须是 2 的幂
    队列深度实例 MI300X 的 rocminfo:Queue Min Size 64, Max Size 131072,Max Queue Number 128
    最后一行是和我们差别最大的一处:AQL 队列最多能装 131072 个包, 而我们每个引擎只有两个槽。深队列可以「把 S 连着依赖一起塞进去然后不管了」; 两个槽做不到,这是提示机制在我们这边格外吃紧的原因。
    05NVIDIA · 原语

    GEQ 计数器与按序 stream

    NVIDIA 没有公开 packet 级规范,但驱动 API 暴露的原语说明了同样的事。

    跨类型 ↔ Stream Memory Operations
    cuStreamWaitValue64 (stream, addr, value, flags);   // 等
cuStreamWriteValue64(stream, addr, value, flags);   // 写
    Driver API · cuStreamWaitValue64 函数说明
    By default, the condition is to wait for
    (int64_t)(*addr - value) >= 0
a cyclic greater-or-equal. Other condition types can be
specified via flags.
    Driver API · CUstreamWaitValue_flags 枚举说明
    CU_STREAM_WAIT_VALUE_GEQ = 0x0
    Wait until (int32_t)(*addr - value) >= 0 (or int64_t for
    64 bit values). Note this is a cyclic comparison which
    ignores wraparound. (Default behavior.)

    这就是我们说的「只增不减的计数器」。 而且比我们的设想多一层:那个循环减法比较忽略回绕, 所以 64 位计数器永远不需要清零 —— 正好消灭了我们文档里「信箱什么时候清」那一整节的坑。

    这些操作作用在设备指针上(不接受 cuMemAllocManaged 的托管内存), 由 stream 在设备侧按序执行,不需要 host 参与。 能力用 CU_DEVICE_ATTRIBUTE_CAN_USE_64_BIT_STREAM_MEM_OPS 查询。

    一条必须记住的官方警告:「Synchronization ordering established through these APIs is not visible to CUDA. CUDA tasks that are (even indirectly) ordered by these APIs should also have that order expressed with CUDA-visible dependencies such as events.」 —— 也就是说这套原语是裸同步,CUDA 自己的依赖跟踪看不见它。 对我们不构成问题(我们本来就是自己管依赖),但说明它在 CUDA 体系里是个逃生舱而非主路。 (历史注记:CUDA 11.x 及更早的文档里这套操作默认关闭,Linux 上需要内核模块参数 NVreg_EnableStreamMemOPs=1;该说明在当前版本文档中已移除。)
    同类型 ↔ stream 按序 + CUDA Graph

    同一 stream 内两个 kernel 严格按序。把 S 推进 P 后面的同一条 stream, S 就自动接在 P 之后,不用回 host —— 和 AQL 的 barrier bit 是一回事。

    CUDA Graph 把整张依赖图交给驱动。cudaGraphUpload() 把 graph 的物理内存映射(以及设备图所需的设备侧资源)提前做掉, 把这部分成本从首次 launch 里摘出来 —— 注意它省的是映射与分配开销, 不是「把执行元数据搬到设备上」,后续的 cudaGraphLaunch() 也不只是一次触发。

    设备侧图启动的几个硬上限值得记:fire-and-forget 120(同一父图一次执行内, 跨 launch 重置)、pending tail launch 255、以及同一张图同时只能有一个 self-launch 排队。前置条件是 instantiate 时带 cudaGraphInstantiateFlagDeviceLaunch, 并且已上传到设备 —— 上传有三条路:cudaGraphUpload()、 instantiate 时请求上传、或先从 host 启动一次(隐式完成上传)。
    06NVIDIA · PDL

    切在另一层的早发

    Programmatic Dependent Launch(PDL,compute capability 9.0 及以上) 常被拿来和早发类比,但它切的层不一样 —— 值得单独说清楚,免得对标对错了位置。

    基线的浪费在两头
      kernel A:  ████████████████▓▓▒▒░░
                              └── 尾部 ramp down:大部分 CTA 已退,SM 大量空闲

  kernel B:                      ░░▒▒▓▓████
                              └── 头部 preamble:算地址、load 常量、搬权重
                                  —— 全都不依赖 A 的输出,却被 stream 语义卡在外面
    机制:三步
    // ① host 侧给 B 打 launch attribute
cudaLaunchAttributeProgrammaticStreamSerialization
    → programmaticStreamSerializationAllowed = 1

// ② 前驱 A 里,快干完时
cudaTriggerProgrammaticLaunchCompletion();

// ③ 后继 B 里
load_constants();  compute_addresses();  prefetch_weights();   // 不依赖 A
cudaGridDependencySynchronize();                              // 到这儿才等
main_body();                                                   // 依赖 A
    CUDA Programming Guide · §4.5 —— 放行条件的准确措辞
    The CUDA driver can launch the secondary kernel when all primary
thread blocks have launched and executed
cudaTriggerProgrammaticLaunchCompletion. If the primary kernel
doesn't execute the trigger, it implicitly occurs after all
thread blocks in the primary kernel exit.

    也就是说 PDL 同样需要一次多对一的汇合:整个 grid 的 block 都触发过或都退出了, 后继才被放行。（官方没有说这是如何实现的 —— 「隐式的 grid 级计数器」是本文的推断,不是文档说法。）

    PDL 的核心概念,也是最值得抄的一点:它把 stream 语义里混在一起的两件事拆开了 —— 调度可见性(B 能否占 SM 开始执行)提前释放, 内存可读性(B 能否读 A 的输出)仍然卡着。

    和我们的差别
    我们的早发PDL
    提前的是什么 任务的下发(分核 → 落槽 → 挂等待;旁路 ready_queue,不是把入队提前) kernel 的执行(占 SM、跑 preamble)
    依赖形状 任意 DAG,扇入最大 16 stream 里是 primary / secondary 一对; 在 CUDA Graph 里用 cudaGraphDependencyTypeProgrammatic 边表达,可任意扇入扇出、不限相邻、不限深度
    对执行侧的要求 不改 kernel,但跨类型要求引擎侧支持「占着槽却既不倒计时也不开跑」的状态, 以及一条跨引擎通知通道(设想是往对面引擎的 SPR 写) 要改 kernel —— 里面插两个内建函数
    省下什么 整趟完成通知回路 整个 prologue

    纠正一个常见误解:PDL 并非「只能同 stream 相邻两个、深度 1」。 官方 §4.5.3 明确支持在 CUDA Graph 中用 edge data 表达 PDL 依赖, cudaGridDependencySynchronize() 的官方注释用的是复数 all primary kernels; cudaLaunchAttributeProgrammaticEvent 还能把触发点录成一个 event 供其它 stream 等待,连 stream 相邻性都不需要。链式(B 既是 A 的后继又是 C 的前驱)也没有限制。

    所以真正的差别不在依赖形状,而在切的层次。

    我们跨类型早发里 S「等信号」的那个点,正好是 cudaGridDependencySynchronize() 该在的位置 —— 现在那个窗口里 S 占着槽但既不倒计时也不算开跑,PDL 那套是在里面跑 preamble。 两者可以叠加。

    CUTLASS 的 Example 63(63_hopper_gemm_with_weight_prefetch) 就是这个用法:当某个输入矩阵(权重)不由上游产出时,在 prologue 期间预取它, 专打 bandwidth-bound —— 和 qwen3 decode 同类负载。

    07缺陷对标

    我们列的两个缺陷,他们怎么解

    缺陷一:一个 bit → 计数器

    我们的判断是对的,而且两家给的答案比我们设想的更强。 直接可抄的是 NVIDIA 那个循环比较:

    (int64_t)(*addr - value) >= 0

    它一次解决三个问题:陈旧信号(单调值分得出新旧)、 回绕(循环减法忽略 wraparound)、 清零时机(根本不需要清零,那个竞态不存在)。

    AMD 走的是另一个方向 —— 倒数到 0 的递减计数器。要注意它附带 「become zero and remain zero」的约束(第 04 页), 单调递增那条路没有这个包袱。

    但要注意一件事:换成计数器解决的是「新旧」,不解决「是谁」。 我们的信号是引擎级、匿名的 —— 如果对面引擎上跑的不是 P 而是别的任务, 计数器照样会涨。

    所以第 03 页那个 free_bitmap 异或不变量 在换成计数器之后仍然需要。两者是正交的:计数器管新旧,异或管身份。

    缺陷二:一格提示 → 一对多

    两家的路子不一样,可以按需要选:

    AMD硬件定长,扇入上限 5

    超了串接多个 barrier packet。定长 packet 加上「handle 0 表示已满足」, 实现简单、位宽固定、硬件代价可控。

    要往跨核早发走,这条更值得参考。

    NVIDIA不设固定扇入

    CUDA Graph 的节点可以有任意入度,由驱动在建图时展开; 或者一个依赖一次 cuStreamWaitValue。

    更灵活,但把复杂度放在了软件层。

    两条都比我们现在的「每个 P 每条通道一格」宽松。 我们那一格今天正好够用,是因为落点只有兄弟槽和对面引擎两个; 一旦允许跨核,落点变几十个,提示表立刻成为瓶颈。
    08原创部分

    没找到哪家做成原语的三处

    措辞先声明清楚:下面是「没有找到哪家把它做成暴露的原语」, 不是「不存在」—— 这类否定性判断永远无法证明。 每一条后面都列出了检索到的近似物。

    1. 匿名的、引擎级的完成信号 + 异或不变量

      我们的通知按引擎发,不认任务身份 —— 一个引擎上任何任务退休都发出同样的信号。 两家的信号都是对象级的:AMD 的 completion_signal 挂在 packet 上, NVIDIA 的 wait value 是一个具体地址,谁完成、通知谁,一一对应。

      近似物三个:HSA 允许多个 packet 共用同一个 completion_signal, 而完成是原子递减 —— 把一条队列上所有包指向同一个信号, 得到的就是一个匿名的、队列级完成计数器(是软件约定,不是独立原语,但形状可表达); HSA 的 read_index 是队列级单调进度计数器,不过它按索引标识进度; Blackwell 的 Cluster Launch Control (clusterlaunchcontrol.try_cancel)返回成功带 ClcID、 失败则是一个不含身份的硬件信号 —— 问的是「有没有活」而非「谁退休了」, 但它是 NVIDIA 目前最接近「无身份硬件通知」的东西。

      而那个 free_bitmap 异或不变量本身,没有找到任何近似物。

    2. 提示按 P 键入而不是按 S 键入

      dispatch 扫到引擎时已经握有 P 的位置,S 的落点直接算出来, 不需要「task_id → 位置」的反查表,也没有陈旧映射的风险。 没有哪家的机制会「查生产者此刻在哪、把消费者放过去」。

      已排除的近似物:CUDA Locality Domains、cluster / preferred-cluster 属性、 green contexts —— 都是程序员指定区域,不追踪生产者。 真近似物:thread block cluster + 分布式共享内存(CC 9.0+) 确实由硬件把协作 block 放到同一个 GPC,是生产者-消费者共置, 但那是同一个 grid 内、按几何而非按运行时位置; AMD 的 hsa_amd_queue_cu_set_mask 是能让你自己实现生产者邻近放置的那个原语,策略仍归你写。

      学术前例是有的,不该说「找不到对应物」: Locality-Aware CTA Clustering for Modern GPUs(ASPLOS 2017)、 Locality-Aware CTA Scheduling for Gaming Applications(TACO 2021), 以及 persistent-threads 里的生产者-消费者共置。

      最贴近的其实在 CPU 侧:Palacharla 等人 ISCA'97 的 dependence-based steering —— 把依赖链导向同一个 FIFO(FIFO 再分布到 cluster 上, cluster 亲和是间接结果,不是直接目标)。它的分配启发式是 「若源指令后面没有别的指令,就接到同一个 FIFO,否则新开一个」 —— 这几乎就是我们的兄弟槽放置加上「恰好一个槽在忙」的异或守卫,只是在指令粒度。

    3. 同类型通道依赖的那条硬件性质

      「核一变空,槽选择必须立刻回到槽 0,而不是下一个仲裁周期」 —— 加上软件侧永远先填槽 0。两条缺一,S 就可能先于 P 被取走。

      这是我们引擎仲裁器的具体性质,两家都不暴露类似的东西。 原因也清楚:他们的队列深、且由 packet processor 用包头的 barrier bit 显式串行化,不需要依赖这种时序细节 —— 见第 04 页那两句规范措辞的对比。

    一条结构性差别贯穿全部三处:他们的队列很深,我们的引擎只有两个槽。 AQL 队列最大 131072 个包(MI300X),而 CUDA 侧没有公开的 per-stream 待启动上限 —— 唯一公开的四位数是 device runtime 的 cudaLimitDevRuntimePendingLaunchCount,默认 2048。 深队列可以「把 S 连着依赖一起塞进去然后不管了」; 我们只有一个兄弟槽、还得跟正常下发抢。 这也是提示机制在我们这边比在他们那边更吃紧的原因 (summary 给出的动因是 painter / dispatch 的职责切分与两轮通知回路; 队列深度这条是本文的补充观察)。
    09数据与优先级

    93% 的边是跨类型

    机会的分布 —— 按边算
    通道边数占全图 2742 条边
    同类型 180 6.6%
    跨类型 2562 93.4%
    实测漏斗 —— 提示与早发
    通道发布提示实际早发提示 → 早发
    同类型 48 – 90 5 – 6 约 5.6% – 12.5%
    跨类型 580 – 612 180 – 280 约 29% – 48%
    两张表分母不同,不能横着比:上表的分母是全图边数,下表的分母是发布出去的提示数。 若要看端到端的「边 → 早发」收益,还得再算一次:同类型 5–6 / 180 ≈ 3%, 跨类型 180–280 / 2562 ≈ 7% – 11% —— 都远低于提示转化率。
    数据来源:提示数与早发数、以及 2742 与 180 取自 summary 第 07 页; 2562、两个占比、三组转化率均为本文推算。

    便宜的那条通道几乎用不上,全部价值压在贵的那条上。

    同类型不需要任何信号,是两条里实现最干净的一条 —— 但它只覆盖 6.6% 的边, 实测每次运行只成功 5 – 6 次。而跨类型覆盖 93.4%, 却正是有 bit → 计数器 问题的那一条。

    结论:工程投入应该压在跨类型通道的健壮性上。 我们自己排的优先级是对的,这组数据是它的量化支撑。

    建议补一个指标

    三个转化率都不高。把「边 → 提示 → 早发」这条漏斗当常规指标 比看端到端吞吐更能定位问题 —— 它把「没机会」、「有机会没发提示」和 「发了提示没接住」分成三段。

    summary 里提到跨类型的队头阻塞目前没有对策 (放置那一刻要求两槽全空,但之后正常下发会把新任务排到还卡着的 S 后面, 让它继承整段等待)。这很可能就是最后一段损失的大头,值得先量化再动手。
