# 早发调度：三处改动

分支：`dev/early-dispatch-cpu-free`
提交：`5f7e7f3` → `648f44b` → `a760394`

方法本身见 [new_summary_outline.md](new_summary_outline.md)；本文只记录这三次改动
各自解决了什么、怎么改的、以及过程中踩到的坑。

---


## 1. 一个 bit 的通知换成单调计数器（`5f7e7f3`）

**问题。** 跨类型早发要让 S 等 P，原本靠一个 bit：P 退休时往对面引擎的信箱写 1，
S 读到 1 就走。陈旧信号靠"放置那一刻清空信箱"挡掉——而它挡得住，只因为清零和写 1
都发生在 dispatch 自己那一轮里，顺序天然确定。

真机上这个前提没了：清零来自 CPU 侧、写 1 来自引擎侧，两者没有顺序保证。于是两个
方向都会错——**读到旧的**（S 把一次无关退休当成自己等的那个，提前开跑），**清掉新的**
（S 放置时清零，而 P 的信号恰好这一刻到达，真信号被抹掉，S 永远等下去）。后者没有
兜底：S 一旦被早发就打上"已下发"标记，正常 ready_queue 路径从此永远跳过它。

**改法。** 每个引擎一个退休计数器，只增不减、永不清零：

| | 谁维护 | 内容 |
|---|---|---|
| `g_sim_cnt[引擎]` | 引擎 | 这个引擎退休了几个（真机上是硬件计数器） |
| `g_placed[引擎]` | AICPU | 我往这个引擎下发过几个 |
| `g_place_seq[任务]` | AICPU | 每个任务当初拿到的序号 |
| `sim_slot_t.wait_target` | 随任务下发 | 要等到的计数值，0 = 不等 |

下发 S 时把 P 的序号作为目标发过去，S 等 `对面引擎计数器 >= target`。因为是**绝对
比较**而不是等一个边沿，S 哪怕在 P 退休之后才被武装也仍然正确——目标已满足，直接
开跑。两个失败方向同时消失：没有陈旧值可读，也没有信号会被清掉。

**两个踩出来的坑。**

- target 必须读 `g_place_seq[p]`（P 自己的号码牌），不能读 `g_placed[引擎]`（取号机
  当前读数）。同类型 plant 就排在 30 行之前，而且打在 P 自己的引擎上，会把取号机推过
  P。读错的话 S 会去等那个同类型兄弟，而不是等 P——顺序断言和 oracle 都抓不到。
- 计数器自增必须攒到一拍结束再统一合并。直接改真值的话，可见性取决于 `sim_tick`
  遍历引擎的顺序：cube→vector 的后继在前驱退休那一拍就开跑，vector→cube 要等一拍，
  而完全不需要信号的同类型反而恒定等一拍——**需要真实跨引擎信号的那条路被建模成了
  最快的**。攒到拍末之后三种统一成一拍。

**新增断言。** 每次退休检查"这个引擎的计数器 == 这个任务当初的序号"，即
**退休顺序 == 放置顺序**。这是 target 方案的地基。它是必要条件不是充分条件——
target 本身取错了仍然能通过。

## 2. 落点条件放宽（`648f44b`）

**问题。** 跨类型 S 原本要求目的地引擎**两个槽全空**，和 `send_task` 的"有一个空槽
就发"不一致，而且专挑完全空闲的引擎去把它卡住。

**改法。** 改成"至少一个空槽"，同时**槽号不能再写死 0**——放宽之后最常见的情形是
槽 0 忙、槽 1 空，写死 0 会直接覆盖掉正在跑的任务，而且 `free_bitmap` 那位本来就是 0，
清零是空操作，没有任何地方会报错。**这两行必须绑在一起改。**

**为什么不会死锁。** 等待图的每条边都严格指向更早放置的任务：S 的 target 来自武装时
已经驻留的 P，而引擎按放置顺序执行，所以一个任务只可能被更早放置的任务卡住。严格
递减的关系成不了环。这个论证**不依赖目的地有多空**。

**代价不是零。**

| | 放宽前 | 放宽后 |
|---|---:|---:|
| 跨类型早发（拥塞工况） | 121 | **260** |
| 每次早发摊到的卡顿拍 | 3750 | **2180**（−42%） |
| 头阻塞拍数 | 116633 | **172680**（+48%） |

早发次数在拥塞下不再衰减（旧规则会掉一半），代价是被阻塞的投机任务现在能占掉引擎
最后一个空槽。净值这个仿真器量不出来（makespan 噪声主导）。

**`place_task` 入口加了一道守卫**：`assert(free_bitmap[type][slot] & mask)`，
放置目标必须真的空闲。

## 3. CSR 前驱列表换成异或累加器（`a760394`）

**问题。** 为了在入度降到 1 时找出那个幸存前驱，原本维护了 7 个数组
（同类型 CSR 三件套、跨类型 CSR 三件套、非 MULTI_PRED 时的单值版）、2 次 `malloc`、
`early_dispatch_init` 里 60 行建表，外加运行时遍历列表找"没被标成 COMPLETED"的那个。

**改法。** 一个数组：

```c
uint32_t g_pred_xor[RING_SIZE];   /* 未完成前驱的异或 */
```

播种和更新都紧贴入度：

```c
/* add_successors：和入度在同一个 if 里 */
predecessor_cnt++;
pred_xor ^= precessor_idx;

/* resolve_dep：和递减在同一行 */
g_predecessor_cnt[succ_id & RING_MASK]--;
g_pred_xor[succ_id & RING_MASK] ^= task_id;
```

入度到 1 时累加器里剩下的就是幸存者，一次类型比较决定进哪张 hint 表。
`early_publish_hint` 从两个版本、~40 行塌成 ~10 行，**不再需要 `tid`**。

**顺带修掉一个漏发。** 旧的查找跟的是 `g_state_buf[tid]` 的 COMPLETED 标记，而
`update_task_state()` 是**整批先打标记**、`resolve_dep()` 才逐条递减。同一批里有
两个前驱时，递减到 1 触发查找的那一刻，真正的幸存者已经被标成 COMPLETED 了——两个
列表都扫不到，函数静默掉出去，一条都不发。实测缺口 **19–27%**：

```
触发点      858（新旧一样）
旧版实发    621–714，差额全部是"扫不到"
新版实发    858
```

异或不受影响，因为它跟的是**递减本身**，不是标记。

**但 plants 没变**（288.5 vs 290.0，n=25）。858 条 hint 只落在 **516 个不同的 P** 上，
最多一个 P 压 18 条，**39% 的发布覆盖掉了一条从没被消费的 hint**——每个 P 只有一格。
所以瓶颈从来不是 hint 供给，**下一个杠杆是让 hint 表每个 P 能存多条**。

**同时修掉一个潜在链接错误**：`CROSS_TYPE` 不带 `MULTI_PRED` 时，`g_cross_hint` 的
声明和定义守卫不匹配。`EARLY_DISPATCH_MULTI_PRED` 这个开关已从代码中删除。
