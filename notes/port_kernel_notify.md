# 跨类型通知机制设计：下发序号 + 单调比较

计算单元侧（kernel.h）通知机制的设计，由人工实现，不走 codeagent 那套流程。但它跟 AICPU 侧
是一套协议的两半，所以 AICPU 要配合的改动也写在这里。

> 本文经过一轮对抗性审查，找出 5 条会让 S 提前开跑的交错序列。下面的内容已按审查结果修正，
> **§4 的论证被重写过——原来的版本论证不完整，结论在一种合理的仲裁器下不成立**。

## 1. 要解决的问题

原型仓的做法是「1 bit 邮箱 + 先清空再等待」。这在原型上是对的，因为模拟时钟由观察者自己
驱动——「读到 P 还在跑」和「S 清空邮箱」之间不可能有任何任务退休。

**真机上这个前提没了**：

```
AICPU 读完成信号 → 看到 P 还在跑 → 下发 S → S 到达 → S 清空邮箱 → S 开始等
                              ↑___________________________↑
                              P 在这段时间里完成、把通知写进邮箱，
                              然后被 S 的清空动作抹掉 → S 永远等下去
```

两个环节都不可控，**缩小窗口解决不了**。根源是「清空」这个破坏性动作。

## 2. 方案

**取消清空**：不让 S 领取信号，让它比较一个单调递增的状态。

### 2.1 AICPU 侧

```c
/* 必须跟 task_id_map 放在同一个结构、用同一套下标 —— 见 §6.1 */
uint8_t dispatch_seq[EXE_TYPE_CNT][AIC_CNT];        /* 每单元一个下发计数 */
uint8_t seq_map[EXE_TYPE_CNT][AIC_CNT][AIC_OSTD];   /* 每个槽当前任务的 seq */
```

- **seq 只能在唯一的放置原语里自增**（原型里是 `place_task()`）。放在别处会烧号，见 §6.2
- **每一个任务**的下发字都带 `seq`——不只早发的。下发 P 时 AICPU 还不知道它会成为谁的 P
- 早发 S 时，下发字额外带**等待阈值** = P 的 seq（从 `seq_map[type][core][忙槽]` 取）

### 2.2 计算单元侧

它不理解这个数字的含义，也不维护计数器，只做三件事：

1. 记住下发时给我的 `seq`
2. 带等待标记时：自旋等到自己这边的邮箱值「不早于」阈值，再开始执行
3. 完成时：**先确保自己的输出数据全局可见**，再把 `seq` 写到兄弟单元的邮箱（无条件，不判断
   有没有人在等——也判断不了）

### 2.3 比较方式与位宽

**用 k = 8 位。** 不要用更窄的：

```c
if ((int8_t)(mailbox_value - threshold) >= 0) { /* 可以开跑 */ }
```

k=8 是原生宽度，上面这行**照抄就是对的**。k=4 或 k=6 时这行是错的（符号扩展位置不对），
需要写成 `(int8_t)((mailbox - threshold) << (8-k)) >= 0`——审查里这是命中概率最高的一条：
每 2^k 次下发必然误判一次，短期联调发现不了。省那几位不值得。

## 3. ★ 触发条件的额外限制：P 必须在槽0

**这一条是修正原设计的关键，不能省。**

跨类型早发只在 **P 位于低编号槽**时触发（原型里就是 `free_slot == 1`，即空的是高槽）。

**为什么**：否则会出现下面这个提前放行——

```
T1  X 占着槽0，P 被放进槽1（下发时槽0忙）。seq(P) = 5
T2  X 退休，槽0 空出
T3  扫描：恰好一个忙槽 → p = P，阈值 = 5，S 被放到配对单元
T4  同一轮的同类型分支（或下一轮的正常下发）把一个新任务放进槽0，seq = 6
T5  仲裁器若是「永远低编号槽优先」→ 槽0那个先跑、先完成、发出 6
T6  S 读到 6 ≥ 5 → 开跑，而 P 还没开始 ✗
```

**注意这不是「硬件不是有序执行」造成的**：上面那种仲裁器完全是有序、非抢占、确定性的——它只是
按**槽号**定序，而不是按**下发顺序**定序。硬件的人被问「是不是严格有序」时回答「是」是诚实的，
这个 bug 照样存在。所以不能靠问那个问题来排除它。

**限制成 P 在槽0 之后**，后来的任务只能进槽1，四种候选仲裁器里三种都保证 P 先跑（唯一的例外
是「严格交替、从不空闲复位」，而那种会让整个早发功能失效，不是这里独有的问题）。代价只是覆盖
率——P 在槽0 的情况本来就占多数（下发到空闲核时优先落槽0）。

**替代方案（覆盖率优先时）**：不限制槽号，改成**冻结 P 所在单元**——只要还有跨类型 S 持着
针对该单元的阈值，就不再往这个单元放任何任务。这样连「严格交替」那种仲裁器都能扛住，但要占住
P 那个单元的一个槽直到 P 完成，**跟不变量 14「早发让位 ready_queue」的取向是冲突的**（这次是
早发反过来霸占资源）。建议默认用槽0限制，覆盖率不够再考虑冻结。

## 4. 正确性论证

设 V = 阈值 = P 的 seq，M = S 那边邮箱的值。释放条件：`(int8_t)(M - V) >= 0`。

### 4.1 不会丢唤醒（§1 那个 bug）

没有任何东西被清空，所以没有东西可丢：

- P 在窗口里完成 → 它已经把 V 写进邮箱 → S 到达一读 `V - V = 0` → 立刻开跑 ✓
- P 还没完成 → 邮箱里是更早的值 → S 等；P 完成写 V → 通过 ✓

### 4.2 不会提前放行

要提前放行，需要在 P 完成之前，邮箱里出现一个「不早于 V」的值。邮箱只由 P 所在单元写，写的是
**该单元上已完成任务的 seq**。所以必须证明：**该单元上任何 seq 不早于 V 的任务，都不可能先于
P 完成**。

分两类：

- **P 之前就在该单元上的任务**：它们的 seq 更小（seq 按下发顺序单调递增，同一个单元的下发都
  经过同一个计数器），写的值早于 V，不满足释放条件 ✓
  - 触发时要求「恰好一个忙槽」（不变量 6），所以触发那一刻其实一个都没有。这一条是为了 §5 讨论
    放宽不变量 6 时用的
- **P 之后才放到该单元上的任务**：它们的 seq 更大，**必须证明它们不会先于 P 完成**。这正是
  §3 那条槽0限制的作用——P 在低槽，后来者只能进高槽，在三种候选仲裁器下都后跑 ✓

**这一步依赖硬件的执行定序**，具体依赖哪一条见 §3。**这是整个方案唯一依赖未验证硬件特性的
地方**，其余部分都是纯软件推理。

### 4.3 不怕被后来的任务覆盖（在半程窗口内）

P 完成写 V 之后，又有任务完成写 V+1，S 才来读：`(V+1) - V = 1 ≥ 0` → 仍然通过 ✓

**但这个免疫是有窗口的，不是无限的**：如果 S 到达前该单元又完成了 ≥128 个任务（k=8），差值绕
过半程会被读成负数，S 转为等待，直到计数再绕回来——或者永远。k=8 时需要 128 次完成落在 S 的
投递延迟里，实际不可能；k=4 时只需要 8 次，就不是不可能了。这是选 k=8 的第二个理由。

### 4.4 为什么 task id 不能代替 seq

试过，两条路都堵死。task id 按**图里的位置**编号，不是按**下发顺序**——同一个单元完全可能先跑
id 40、后跑 id 20（两个子图 id 交错，进哪个核由「最低位空闲核」决定，跟 id 无关）。

- 用 `≥` 比较 → 邮箱里残留一个更大的旧 id → **提前放行**
- 用 `==` 精确匹配 → 被后续任务覆盖 → **永远等待**

根本原因：task id 携带「图里的身份」，这里需要「这个单元上的时间先后」。

注意这跟不变量 10d 的**刻意不对称**：task id 禁止复用，seq 必须复用（回绕）。两个量干两件事，
别让人把它们混成一个。

## 5. 不变量 6 能不能放宽（原设计说能，修正为：不建议）

原设计说 seq 带上了身份，所以「两个槽都忙」的单元也能安全触发。**这个说法只对了一半**：

- 对 **P0 排在 P 前面**（P0 seq 更小）这个方向，确实安全——P0 完成写的值不满足阈值 ✓
- 但对 **P1 排在 P 后面**（P1 seq 更大、却可能先跑）这个方向，就是 §3 那个 bug，放宽之后会多
  开一个入口

而 §3 的槽0限制已经把这个方向堵住了。所以：**先不放宽**，等 §3 的硬件定序假设被实测确认之后
再单独评估。

## 6. 实现坑（都会咬人，且不报错）

### 6.1 ★ `dispatch_seq` / `seq_map` 必须跟 `task_id_map` 同作用域、同下标

原型里 `task_id_map` 在 `ctrl_t` 里（每个下发线程一份），核下标是**线程局部**的。如果把
`dispatch_seq` 写成文件级全局并用线程局部核下标去索引，两个线程的「局部 5 号核」会撞进同一个
计数器——计数被别的单元推着涨，阈值跟邮箱脱节，**提前放行**。

另外 `++` 一个跨上下文共享的 `uint8_t` 是非原子读改写，正是不变量 10c 那个竞态。

### 6.2 ★ seq 只能在唯一的放置原语里自增

有两处会「烧号」（分配了 seq 却没真的放置任务）：

- 正常下发路径里的重复拦截：`continue` 时**不消耗核**，所以一批里每个重复项都会在同一个核上
  烧一个号。实测这个计数是 200-300 量级
- 跨类型 hint 在目的地忙时**保留、每轮重试**（不变量 12），每轮重试都会烧一个

k=8 时余量 128，烧几个无所谓；k=4 时余量只有 8，烧 7 个就够提前放行了。把自增放进放置原语
（原型里的 `place_task()`，每次调用必然放置）可以结构性杜绝。

### 6.3 阈值要从**忙槽**取，别取反

原型扫描时算的是 `free_slot`（空槽），阈值必须来自 `free_slot ^ 1`。取反了会拿到兄弟槽的 seq：
偏大则白等，偏小则**提前放行**，而且看起来完全合理，查不出来。

### 6.4 两个类型下标在同一处交替出现

跨类型分支里，阈值来自 **P 的类型**命名空间，S 自己的 seq 来自**配对类型**命名空间：

```
threshold = seq_map[type ][core][busy_slot]   /* P 的单元 */
seq(S)    = ++dispatch_seq[ctype][core]       /* S 的单元 */
```

两个下标都是小整数、都合理，弄反了不会有任何诊断。

### 6.5 邮箱的上电初值必须有人负责

§2 假设邮箱从 0 开始、seq 从 1 开始。但**按 §2.2 只有兄弟单元会写这个邮箱**，AICPU 可能根本
没有写它的通路。那么：谁来清零？跨图重跑、进程重启时又是谁？

留一个上一轮的残值会直接出事：残值 5、新阈值 1 → `(5-1)=4 ≥ 0` → **S 立刻开跑而 P 没跑**；
残值 12、阈值 1 → 等一个可能永远不来的值 → **挂死**（不变量 25：没有超时兜底）。

这是一个**没有主人的前提**，必须在设计阶段指定：要么 AICPU 有写通路负责清，要么每个单元开机
跑一个 dummy kernel 把自己的邮箱清掉，要么硬件复位保证。

### 6.6 ★ 内存序：两侧都要

- **生产侧**：P 的输出数据必须在写 seq **之前**全局可见。否则 S 按时开跑、读到的是垃圾。
  （AICPU 侧那个 `volatile` 是另一回事，见不变量 21）
- **消费侧**：自旋读邮箱必须是 `volatile`/acquire 语义，否则编译器会把读提到循环外 → 死循环
- **邮箱语义必须是「电平保持、后写覆盖、读不消费」**。这不是一个开放问题，是**硬性要求**：
  如果读会消费，S 自己等成功之后就把值抹了，后面任何阈值不高于它的 S 都会挂死

### 6.7 下发字目前没有格式，而且跟握手复用同一个寄存器

原型里下发写的是**裸 task_id**，而握手往**同一个寄存器**写 `HAND_SHAKE_VAL | 地址位`。所以
「能不能挤出 17 位」不是一个是非题——得先定义一套字段布局，并保证新字段不跟握手的值域重叠。

### 6.8 每个任务都多一次跨核写

§2.2 第 3 步要求**所有**单元上的**所有**任务在完成时都做一次跨核写。这是一个降延迟的功能，却
给每个 kernel 的退出路径加了一次跨核 store，而且每个 kernel 都要能算出兄弟单元的邮箱地址。

## 7. 仍需向硬件确认（按重要性排序）

1. **同一个单元上多个任务的执行定序，具体由什么决定？** 不要问「是不是有序」——那个问题
   区分不出 §3 那个 bug。要问的是：**一个单元从「只剩高槽有任务」变成「两个槽都有任务」时，
   先执行哪一个？** 以及「核变空之后，下一个执行的是不是立刻回到低槽」。
2. **计算单元能不能读到自己这边的邮箱？** 文档里那条硬约束说 LSU 够不到 SPR 的 MMIO 窗口。
   若为真，接收端整个不成立——不管邮箱里放的是 bit 还是 seq。
3. **跨核写能写进对方的什么地址空间？** 只有 SPR，还是也能写进对方的本地内存？后者能绕开
   第 2 条。
4. **下发字能不能容纳 17 位新字段**（seq 8 + 阈值 8 + 等待标记 1），且不与握手值域冲突？
5. **`CrossCoreSetFlag`/`CrossCoreWaitFlag` 的确切语义**：电平还是边沿？`WaitFlag` 会不会
   消费标志？能不能带值比较？如果本身就支持带值，可能不用自己造这套。
6. **跨核写和数据可见性的先后**：有没有 release 语义，还是需要显式 flush + fence？
7. **配对是否严格 1:1？** 1:2 下一个邮箱会有**两个写者、两套独立计数**，seq 命名空间直接塌掉，
   整个方案无意义。seq 方案看起来像能推广到 1:2，其实不能——这一点比 1-bit 方案更隐蔽。
